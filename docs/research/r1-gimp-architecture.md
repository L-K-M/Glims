# Round 1: GIMP core and GUI separability (source study)

# GIMP core vs. GTK UI: how separable is it for a native (AppKit/Rigi or Qt) front-end?

**Short answer:** GIMP's core is cleanly separated from its GTK UI, and the build files prove it. The tools and canvas layer are not separated: they are tied to GDK event types and to the GTK canvas widget. A native front-end can reuse about 350k lines of core code unchanged, but must replace or heavily adapt about 400k lines of GTK-bound code.

**Source examined:** GIMP master, commit `2aef5e7cda0fa5a198f5978d365b5ace44a4eb47` (2026-11-03), version `3.3.1`. It is a shallow clone at `/tmp/gimp-fork-research/gimp`, later deepened to 12 months of history with `git fetch --shallow-since`. I read it with git, grep, wc and sed only. Nothing was built and no repo script was run. Line counts are `wc -l` of .c, .h and .cc files, headers included. "Verified" means read in source or build files; "inferred" means my estimate.

## 2. Headless build (verified, `app/meson.build`)

- `gimpconsole_exe` is built from the same `main.c` and app sources with `-DGIMP_CONSOLE_COMPILATION`.
- It links only:
  - the 14 GUI-free static libraries: core, file, file-data, gegl, internal-procs, layer-modes, layer-modes-legacy, operations, paint, path, pdb, plug-in, text, xcf, plus config;
  - the base libraries: libgimpbase, libgimpcolor, libgimpconfig, libgimpmath, libgimpmodule, libgimpthumb.
- Its dependency list (`gimpconsole_deps`) has cairo, pango, gegl, gexiv2 and lcms, but no gtk3 and no libgimpwidgets.
- In `main.c` (line 53) and `app.c` (line 65) the GTK includes and `gui_init()` sit behind `#ifndef GIMP_CONSOLE_COMPILATION`. The console build uses `GimpConsoleApp` (a GApplication); the GUI build uses `GimpApp` (a GtkApplication, `gui/gimpapp.c:56`).
- The designed seam is the `GimpGui` vtable in `core/gimp-gui.h`, with 27 hooks. They cover: display_create/delete, progress_new, show_message, wait, pdb_dialog_new/set/close, query_profile_policy, query_rotation_policy, get_mount_operation, recent_list, and window handles.
  - `gimp_gui_init` sets the hooks to NULL; core falls back when they are NULL (for example, `gimp_create_display` returns NULL).
  - `gui/gui-vtable.c` (1,128 LOC) installs all 27 hooks.
- Core defines an abstract `GimpDisplay` (`core/gimpdisplay.c`, 217 LOC). The GTK side subclasses it as `GimpDisplayImpl` in `display/gimpdisplay.h`.

**What this proves:** the 14 GUI-free libraries link with no GTK at all, and the intended way in for a different UI is "implement GimpGui plus a GimpDisplay subclass". Left out of gimp-console: actions, dialogs, display, gui, menus, propgui, tools, widgets and libgimpwidgets.

One more consequence: tool registration (`gimp_tools_init`, `gui/gui.c:547`), menus, actions, sessions, input devices, controllers and the clipboard are all set up only by the GUI build. Paint infos are registered in core (`core/gimp.c:320`).

## 3. Tools (verified unless marked)

`GimpToolClass` in `tools/gimptool.h` passes GDK types through its virtual functions:
- `GdkModifierType` in button_press, motion, oper_update and the other pointer handlers;
- `GdkEventKey*` in key_press and key_release;
- `GimpUIManager*` in get_popup;
- the struct itself holds a `GimpCanvasItem*` and a `GtkWidget *progress_grab_widget`.

How tied the tools are to the GTK display:
- 47 of 116 tool .c files call `gimp_display_get_shell`, 154 times in total.
- They use 36 distinct `gimp_display_shell_*` functions and read 18 `shell->` fields directly (unit, show_all, canvas, disp_width and others).
- There are 770 references to Gdk event or modifier symbols.
- `display/gimpdisplayshell.h` itself subclasses `GtkEventBox`.
- 6 tools use `GimpToolGui`, the GTK dialogs shown on the canvas (86 calls).

Tool options:
- The 72 options files hold 15.5k LOC with 760 gtk_ calls.
- Paint tool options are GTK-free models in app/paint.
- Options for the other tools mix the GObject model and the `_gui()` widget code in one file (for example, `gimpmoveoptions.c` lines 1–216 are model, 217–276 are GUI).

The text tool is the most GTK-bound:
- `widgets/gimptextbuffer.c:58` subclasses `GTK_TYPE_TEXT_BUFFER`.
- `gimptexttool-editor.c` has about 200 GtkTextBuffer/GtkTextIter references and 26 GtkIMContext references.
- The text layout and layer code in app/text is GTK-free (pango).

The algorithms themselves are GTK-free and live in core:
- **Painting:** the paint tool only drives `gimp_paint_core_*` (start, interpolate, paint, finish) from `paint/gimppaintcore.c`. It does so on a dedicated thread (`g_thread_new ("paint")`, `gimppainttool-paint.c:113`).
- **Transform:** `gimp_drawable_transform_*` in `core/gimpdrawable-transform.c`, plus `gimp-transform-utils.c`.
- **Selection:** `gimp_channel_select_*` and `gimp_pickable_contiguous_region_*`.
- **Other:** bucket fill, gradient, crop, snapping (`core/gimpimage-snap.c`).
- The PDB exposes most of these for non-interactive use.

What remains in app/tools is interaction state machines, on-canvas handles and options UIs: 66k non-options LOC. 43 files (24.4k LOC) contain no gtk_ or Gtk symbols at all, but they still use GDK types and the display shell.

**What a new front-end must provide (inferred):** either
- (A) a GTK-free shim of the display shell plus GDK-type replacements, so the existing 49 tools keep working, while rewriting the options UIs and GimpToolGui; or
- (B) a reimplementation of all 49 tools' interaction code against the core APIs.

## 4. Canvas rendering (verified)

The chain from image to screen:
1. `core/gimpprojection.c` builds the composited image lazily as a GeglBuffer. It uses `GimpTileHandlerValidate` and `GimpChunkIterator`, rendering in chunks from `g_idle_add_full` (lines 522 and 743).
2. When a region changes, the projection emits an `"update"` signal; `display/gimpdisplay-handlers.c:60` listens to it.
3. `display/gimpdisplayshell-render.c` (536 LOC) gets the pixels:
   - `gimp_pickable_get_buffer` → `gegl_buffer_get` or `gegl_node_blit`, at a given scale, in babl format "cairo-ARGB32";
   - then `gimp_color_transform_process_buffer` for the display color profile and display filters;
   - into a cairo image surface.
4. Canvas overlays (`GimpCanvasItem`) are GimpObject subclasses drawn with cairo (303 cairo calls, 8 gtk calls in 60 files, 14.3k LOC), but 28 of 30 call into the display shell.
5. The on-canvas tool widgets (`display/gimptool*.c`, 23k LOC) are GimpObject subclasses with almost no GTK calls (45), but heavy GDK type use (317 references).

All of this can be driven from a non-GTK view. A native NSView or CALayer can request any babl format and region from the projection and register a priority rectangle via `gimp_projection_set_priority_rect`.

Display code without any Gtk symbols totals about 33.7k LOC (.c only). It is reusable through a shell shim plus a cairo surface; cairo is already a core dependency.

## 5. Plug-ins and filter dialogs (verified)

**Plug-ins run as separate processes** and talk to GIMP over a wire protocol (`libgimpbase/gimpprotocol-private.h`):
- `GP_PROC_INSTALL` carries a `GPParamDef` for each argument, with types int, unit, enum, choice, boolean, double, string, color, ID, resource, file, curve and export options.
- On the app side, `_gimp_gp_param_def_to_param_spec` (`app/plug-in/gimpplugin-message.c:820`) turns these into real GParamSpecs.
- Run modes are `GIMP_RUN_INTERACTIVE`, `NONINTERACTIVE` and `WITH_LAST_VALS`.

**How plug-ins build their dialogs:**
- On the plug-in side, `GimpProcedureConfig` (`libgimp/gimpprocedureconfig.c`) is a GObject whose properties are the procedure's arguments.
- It stores last-used values under `plug-in-settings/<TypeName>` and per-image values as parasites.
- `GimpProcedureDialog` (3,340 LOC, GTK) builds widgets from those GParamSpecs (`g_object_class_list_properties`, line 2029). Grouping, notebooks and sensitivity rules are set up in plug-in code (`fill_frame`, `fill_notebook`, `set_sensitive_if_in`).

Plug-in survey:
- 93 files use a procedure dialog;
- 30 use custom `gimp_dialog_new` dialogs;
- 26 have their own previews;
- 9 use a GtkDrawingArea.

Registered procedures: 60 image, 68 load, 55 export, 17 thumbnail, 4 vector-load, 20 generic, 1 batch.

**A native host can do this:** it already holds the GParamSpecs, so it can auto-generate dialogs and run procedures with `NONINTERACTIVE`, reusing the stored last values. That covers most simple filters and file options. (The approach is verified as possible; how well it turns out is inferred.)

**What is lost:**
- the layout and grouping each plug-in defines in its own code;
- previews inside plug-ins, such as JPEG export's size and quality preview;
- the large custom editors: gfig, gimpressionist, imagemap, ifs-compose, lighting, map-object, fractal-explorer, flame.

Any plug-in run interactively still opens GTK windows, so GTK3 must still be shipped.

**GEGL filters run inside the app (verified):**
- About 130 GEGL operations appear in the Filters menu (`actions/filters-actions.c`).
- `actions/gimpgeglprocedure.c` takes one of two paths:
  - non-interactive: `gimp_drawable_apply_operation_with_config`, in core;
  - interactive: `GimpFilterTool`/`GimpOperationTool` in tools.
- Their UI is generated by `propgui/gimppropgui.c`:
  - a generic builder (378 LOC) that dispatches on GParamSpec type plus GEGL metadata keys (unit, axis, role, visible, sensitive, label, description);
  - 17 hand-written GUIs for specific operations (color balance, hue-saturation, supernova and others);
  - the metadata expression evaluator `gimppropgui-eval.c` (1,043 LOC) is GTK-free.
- On-canvas controllers (line, transform grid, gyroscope, focus) come from `tools/gimpfiltertool-widgets.c`.
- Live preview, split preview, commit and abort all live in core `GimpDrawableFilter` (`core/gimpdrawablefilter.c`, `set_preview`, `set_preview_split`, `commit`, `abort`). This fits Rigi's try-on popover with live preview and a single undo step very closely (inferred).

## 6. Other coupling (verified)

- **GLib main loop:**
  - core and plug-in code use `g_idle_add` and timeouts (core has 10 such call sites);
  - synchronous plug-in calls spin nested loops (`g_main_loop_run`, `app/plug-in/gimppluginmanager-call.c:308–330`);
  - GEGL work runs on threads, and painting uses its own thread.
  - Upstream is moving off `gtk_main` toward `GMainContext` (commit `e90dbe28`, 2026-08-21), which helps a native host.
- **Config:** the gimprc class chain `GimpGeglConfig → GimpCoreConfig → GimpDisplayConfig → GimpGuiConfig → GimpDialogConfig → GimpPluginConfig → GimpRc` is all GTK-free (app/config). The sessionrc, devicerc and controllerrc formats are GTK-side.
- **Menus and actions:**
  - `GimpAction` is a GObject interface; the action implementations, `GimpActionGroup` and `GimpMenuModel` implement GIO's `GAction`, `GActionGroup` and `GMenuModel`;
  - they still make a few GTK calls: `gimpaction.c` has 36 (accelerator parsing, proxy widgets);
  - `menus/*.ui` (39 files) are GMenuModel XML with `app.*` action names, so they can be mapped to NSMenu;
  - about 1,139 action entries exist; the declarative `*-actions.c` tables are 15.4k LOC, the `*-commands.c` callbacks 19.6k, and 20 of the 44 command files open GTK dialogs.
- **Undo:** the image undo stack in core is GTK-free and emits an `"undo-event"` signal. Some tools keep their own undo state for in-progress edits (`can_undo`/`undo` in `GimpToolClass`).
- **Model signals:** GimpImage has 33 signals, GimpContext 20 and GimpContainer 5. Previews come from `gimp_viewable_get_new_preview`/`get_new_pixbuf` in core. Inferred: these map naturally onto NSTableView/NSOutlineView data sources and onto Rigi's PaletteCenter retargeting to the front document.

## Reuse map

**Reuse as-is (verified GTK-free, ~394k):**
- app/core, pdb, operations, paint, plug-in, path, xcf, config, text, gegl, file, file-data (348.5k);
- libgimpbase, libgimpcolor, libgimpconfig, libgimpmath, libgimpmodule, libgimpthumb (45.5k);
- the plug-in processes themselves;
- `menus/*.ui` as data.

**Reuse with adapters (strategy A, roughly 100–140k):**
- display GTK-free code (~33.7k): tool widgets, canvas items, transform/scroll/render math, motion buffer, modifiers manager. Needs a display-shell shim and a cairo surface hosted in an NSView or CALayer.
- tool behaviors (66k): need GDK-type replacements (770 references) plus a shell shim covering 36 functions and 18 fields.
- the `*-actions.c` tables (15.4k) and the GTK-free half of the commands.
- the GAction/GMenuModel classes in widgets, the view renderers (~4k), propgui-eval (1k).
- new code to write: a GimpGui vtable implementation (27 hooks; the current GTK version is 1.1k), a GimpDisplay subclass, and a GimpCoreApp implementation.

**Sizing (inferred):**
- Strategy A replaces about 230–260k lines of GTK C.
- Strategy B (reuse only GTK-free code) replaces about 330–370k, because tools and canvas logic are added.
- Swift/AppKit is usually much shorter than GObject C. My guess: 80–150k Swift for near-parity under A, or 30–60k for a focused professional subset.
- The plug-in GTK UIs (306k C in total) stay GTK unless dropped.

## Hardest technical risks

1. **Main-loop integration (verified mechanism, inferred difficulty).**
   - Core needs a running GLib main context: idle-driven projection rendering, plug-in IPC watches, nested `g_main_loop_run` during plug-in calls, `gimp_wait`.
   - On macOS this means bridging `GMainContext` and `NSRunLoop`, nested loops included. GTK's Quartz backend does this today; you would have to rebuild it.
   - All core GObject calls must stay on the main thread, even though painting and GEGL run on their own threads.
   - With Qt on Linux this is easier, since Qt's GLib event dispatcher is normally the default (inferred).
2. **Tools/display coupling.**
   - GDK types are baked into the `GimpToolClass` virtual functions, and `GimpDisplayShell` is a `GtkEventBox`.
   - The text tool sits on `GtkTextBuffer` and `GtkIMContext`.
   - Path A means a deep patch set on code upstream changes about 80 (tools) plus 64 (display) times a year, and upstream's GTK4 preparation edits exactly these event APIs. Path B means rewriting 49 tools.
3. **Plug-in UIs are out-of-process GTK.**
   - Native auto-generated dialogs plus `NONINTERACTIVE` runs work for many procedures.
   - They lose plug-in-specific layout, sensitivity rules and previews (export dialogs included), and the large editors remain GTK.
   - You end up shipping GTK3 anyway and accepting a mixed look, or cutting features.
4. **Upstream treadmill.**
   - About half of app/ commits touch the GUI directories, and app/ internals are private static libraries with no stable API.
   - Every new upstream feature (link layers, new on-canvas filter controls, 3.4 work) needs a native UI built again.
   - GPLv3 covers the whole combined app. Rigi's Unlicense is compatible, but GPLv3 complicates App Store distribution (inferred).
5. **Rendering and input fidelity.**
   - The display pipeline has to be reproduced: render cache, priority-rectangle chunk rendering, monitor ICC transform (from NSScreen color space), display filters, selection-mask overlay, HiDPI `render_scale`, rotate and flip.
   - Cairo overlays must be composited on Core Animation or Metal at good speed.
   - NSEvent tablet pressure, tilt and rotation must be mapped into `GimpCoords`, plus motion smoothing and device curves.
